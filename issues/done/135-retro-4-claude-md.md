# retro: 記事ベストプラクティスの未反映4点を CLAUDE.md に追加

## 参照記事

https://qiita.com/uno_ha07/items/5820d195510861b5be71

Boris Cherny（Anthropic スタッフエンジニア）の知見を基にした CLAUDE.md ベストプラクティス。

## 追加したい4点

### 1. 自己改善ループのタイミング

現状の CLAUDE.md には `self-improve` の呼び方は書いてあるが「いつ retro issue を起票するか」が書かれていない。記事の核心は「ミスが起きたらその場で即座に記録する」という即時性。

- ユーザーにミスや改善を指摘されたとき → その場で retro issue を起票して self-improve を呼ぶ
- セッション内で同じ種類のミスが2回以上起きたとき

### 2. 「スタッフエンジニアはこれを承認するか？」自問

タスク完了前・コミット前の品質チェックポイントとして機能する。現状は暗黙。

- コミット前・issue close 前に「このコードをスタッフエンジニアがレビューしたら承認するか？」と自問する
- feat と fix が混在していないか、テストが不十分でないか、ドキュメントが更新されているかを確認する

### 3. 根本原因を特定・一時的な修正を避ける

現状は `unwrap()` 禁止などの具体ルールはあるが、設計姿勢としての原則が明文化されていない。

- エラーや問題を回避するのではなく、根本原因を特定して解決する
- `--no-verify` や `#[allow(...)]` などの「とりあえず通す」対処は行わない

### 4. Plan モードをいつ使うか

現状は使い方は書いてあるが「どんなときに使うか」が不明確。

- 3ファイル以上を変更するタスク
- breaking change を含むタスク
- 設計判断が複数ある場合
