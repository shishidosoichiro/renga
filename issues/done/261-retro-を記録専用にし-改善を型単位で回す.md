# retro を記録専用にし、改善を型単位で回す

## 問題

retro が3か月起票されていない。retro スキルが、起票のたびに self-improve の起動まで求めるためだと考える。

- 最後の retro は #226（2026-07-04）。#227〜#260 では0件
- 6月起票の retro が6件 open のまま（#173・175・177・181・197・198）
- `.claude/skills/retro/SKILL.md` は、起票直後に `Agent(subagent_type="self-improve")` の起動を求める。`.claude/rules/issue-management.md` の retro 起票ルールも同じ
- 宣言した「セッション振り返り」形式が使われていない。直近の retro（#181・#197）は、推測した対策付きの数行の散文である

## 仮説

記録と改善が1つの手順に束ねられているので、記録するたびに改善の重い作業が始まる。その結果、記録そのものが避けられている。別の運用でも、記録と改善を分けると記録が再開した経験がある。

## 取り込み案

1. **retro スキルを「記録だけ」にする**: 改善は「同じ型の retro が2件たまったとき」に別の工程で回す
2. **retro 本文を3節にする**: 「観測／そのとき何が見えていたか／推測」。推測した対策をそのまま書くと、誤ったルールが入る。#197 はこの形をしている
3. **retro に型ラベルを付ける**: 例は `unverified-premise`（前提を確かめずに進めた）、`unread-source`（一次資料を読まずに書いた）
4. **self-improve の Step 6 を直す**: 「1変更 = 1根拠」をやめる
   - 理由: retro 1件ごとに1行を足す方式は CLAUDE.md を太らせ、同じ型の再発を止めない
   - 代わりに、改善策の出口を複数用意し、3つの問いで選ぶ
     - 出口の例: CLAUDE.md・スキル・hook・テスト・CLI の機能・何もしない
     - 問い1: 既存のルールは読まれていたか
     - 問い2: 機械で判定できるか
     - 問い3: 誰が、いつ、その知識を要るか
5. **CLAUDE.md の純増を0に保つ**: 規律として入れる。計測は `wc -m` で足りる（現在 2224 文字）
6. **agent-config-reviewer を強化する**: 次の2つを足す
   - 確認項目「推測の追認」「事実の独立再検証」
   - 停止条件「2周で要修正が残れば起票」
7. **既存の open の retro 6件を棚卸しする**: 新しい形式で書き直す

## 見送るもの

- **commit／push 前のゲート hook**: 自己申告のゲートは、別の運用で効かずに廃止された
- **エージェント間のロック・ロールバックの仕組み**: Renga は単一のエージェントで回している
- **rules から skills への移行**: Renga はリポジトリ1つで、ルートから起動するため見送る。ただし `paths` 付きの rules が実際に載るかは、新しいセッションで確かめる

## 進め方

この変更は `.claude/` を変えるので、規約上は retro → self-improve を通す。ただし、変える対象が retro の流れそのものである。そのため最初の1回は、宍戸さんの承認を得てから self-improve に渡す（2026-10-07 に方針は承認済み）。

## 再検討の条件

- コミット50件あたりの retro 件数が6月の水準を下回ったら見直す。6月はコミット89件に対し retro が約25件だった。8〜9月はコミットが0件で、件数だけでは活動の空白と区別できない

- 「機械で判定できるなら hook」の問いで、hook やテストが増えすぎたら見直す
