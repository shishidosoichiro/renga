# make_slug が長い日本語タイトルで単語の途中で途切れる

## 問題

`make_slug`（`src/issue.rs`）は Unicode 文字単位で 30 文字にカットするだけで、
日本語には分かち書きの区切りがないため複合語・文節の途中でぶった切られる。
本 issue 自身のファイル名（`214-make-slug-が長い日本語タイトルで単語の途中で途切れ.md`）が
末尾の「る」が欠落した実例になっている。

## 前提

slug はあくまで人間可読のラベルで、一意性は `N-` の ID 部分が担保している。
実害は「読みにくい」レベルに留まり、正確性やデータ整合性の問題ではない。

## 対応案

形態素解析（MeCab/Sudachi 等)を依存に追加するのはやりすぎ。素朴に直せる範囲で:

- 区切り文字（スペース・記号）の直前で切る best-effort（区切りが30文字以内に
  無ければ従来通り文字数カットにフォールバック）
- または上限を 30→40 程度に伸ばして頻度を下げる

どちらか、または両方の組み合わせで検討する。

## 検討の経緯と決定

そもそも「30文字」という上限自体に文書化された根拠が無いことが判明した。
Rust 実装移植前の Python 版 `bin/fbim` の `slug[:30]` まで遡っても、
導入コミットに理由の記載は無い（`found_at:0.1.0`）。

以下の2案を実装しレビューに出したが、いずれも実装バグが繰り返し見つかったため撤回した。

1. **区切り文字 `-` の直前で切る、ただし予算の2/3以上を保持できる場合のみ**:
   閾値ちょうどの境界値で後続の単語が丸ごと消えるケースが見つかった（#217）。
2. **文字のスクリプトクラス（漢字・ひらがな・カタカナ）の切り替わりで切る**:
   区切り文字が無い連続した日本語にも効く利点はあったが、`々`（踊り字）が
   判定から漏れて逆に複合語を分割する（#218）、境界探索の off-by-one で
   不要な切り捨てが起きる（#219）という新たなバグを持ち込んだ。

いずれも「自動生成されるファイル名の見た目が少し読みやすくなる」という
cosmetic な利益のために、恒常的にバグを生み続ける複雑さを持ち込んでいた。
slug の一意性は常にファイル名先頭の数値 ID が担保しており、slug 自体は
人間可読性のための補助に過ぎない。

**最終決定**: 切り詰めの単位を文字数ではなく**バイト数**にする（UTF-8 で
日本語1文字は概ね3バイト、ラテン文字は1バイトであり、バイト数は文字数より
「情報量」に近い指標になる）。上限は **80バイト**とする（80カラム端末という
広く知られた慣習に基づく、説明可能な数値）。カットオフが UTF-8 のマルチバイト
文字の途中に来た場合は、直前の有効な文字境界まで切り捨てる（
`str::is_char_boundary` で判定、「最大80バイトを超えない」という単純な
不変条件を保つため）。スクリプト判定・区切り文字の距離判定など、単語境界を
推測しようとするロジックは一切持たない。

連続した日本語フレーズがバイト境界で単語の途中で終わることは引き続き
起こり得るが、これは辞書ベースの形態素解析なしには解決できない、受け入れられた
制約とする。
